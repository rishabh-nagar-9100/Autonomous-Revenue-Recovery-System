## Post-MVP Expansion Architectural Decisions
- [2026-08-27] Sandbox API failure does not silently fall back to mock execution. `EXECUTION_MODE=sandbox` returns structured `FAILED` or `PENDING_RECONCILIATION` on API error. Explicit `DEMO_FALLBACK_TO_MOCK=true` is the only permitted fallback path and is audited.
- [2026-08-27] B2B receivables use domain-specific playbooks (`receivable_overdue`, `promise_to_pay_missed`) with their own action sequences. The existing `recent_overdue` payment-recovery playbook entry `["reminder", "payment_link"]` is never globally modified.
- [2026-08-27] `PENDING_RECONCILIATION` is a strict state-machine invariant blocking further financial/recovery actions until resolved. Network timeouts must never be treated as automatic payment failures when financial outcome is uncertain.
- [2026-08-27] Unknown root causes may trigger at most one bounded clarification attempt (`WAITING_FOR_CUSTOMER_INFO`). No money/payment action occurs during info-gathering. Customer silence or invalid response escalates. Recovery eligibility is re-checked before resuming playbook.
- [2026-08-27] Voice is an interface layer to the existing recovery engine, not a financial decision maker. Contact eligibility (opt-out, DND, phone validity, recovery validity) must be verified before initiating any outbound voice interaction.
- [2026-08-27] Post-MVP capabilities are gated by explicit feature flags (`EXECUTION_MODE`, `B2B_ENABLED`, `INFO_GATHERING_ENABLED`, `VOICE_ENABLED`, `FAULT_INJECTION_ENABLED`, `DEMO_FALLBACK_TO_MOCK`). Default settings remain safe with zero implicit external calls.
- [2026-08-27] Lightweight versioned database migration strategy (`schema_migrations` table) manages all post-MVP schema additions predictably and reproducibly.
- [2026-08-29] Monotonic Payment-State Transition Invariant: External webhook ordering does not dictate internal financial state ordering. State transitions are strictly monotonic (`DETECTED` → `IN_PROGRESS` → `PENDING_RECONCILIATION` → `RECOVERED` / `ESCALATED` / `FAILED`). `RECOVERED` is a terminal state that can never be reverted by late/out-of-order webhooks. Duplicate `payment_success` webhooks create receipt audit entries but yield zero duplicate financial transitions.
- [2026-08-29] Razorpay Python SDK (`razorpay`) approved for inclusion in `requirements.txt` for Phase 10 sandbox client adapter.
- [2026-08-29] Reconciliation Timeout Policy: Maximum of 3 reconciliation attempts OR 24 hours elapsed (whichever occurs first) without resolution forces human escalation (`ESCALATED`).
- [2026-08-29] Information-Gathering Recovery Window: Set to 7 days (configurable). If customer responds after 7 days, recovery eligibility check fails and routes to escalation rather than resuming automated playbook.
- [2026-08-29] Voice Testing Strategy: Automated unit/integration tests use mocked STT/TTS adapters with deterministic transcripts. Selection of specific real STT/TTS providers is deferred to Phase 14 integration phase.
- [2026-08-29] Webhook Receipt Semantics: `webhook_events.event_id` is a unique PRIMARY KEY representing unique webhook events. Duplicate webhook deliveries are deduplicated by `x-razorpay-event-id` and return HTTP 200 `duplicate_skipped` without inserting duplicate database rows or duplicate financial outcomes.
- [2026-08-29] Financial State Semantics: `payment.authorized` represents authorization pending capture and does NOT transition a risk event to `RECOVERED`. Only confirmed success events (`payment.captured`, `payment_link.paid`) mark a risk event `RECOVERED`.
- [2026-08-29] Orchestration Boundary: Status reconciliation (`reconcile_payment_status`) with `auto_resume=True` automatically resumes the recovery loop upon confirmed failure (`reconciled_failed`) by invoking `handle_outcome(conn, risk_id, current_action_index, ExecutionStatusEnum.FAILED)`, maintaining a clean orchestration boundary without manual test glue.
- [2026-08-29] Enum & State Semantics: `ExecutionStatusEnum` represents action-level execution result (`SUCCESS`, `FAILED`, `PENDING_RECONCILIATION`), while `EventStatus` represents the overall risk event / workflow lifecycle state (`DETECTED`, `IN_PROGRESS`, `PENDING_RECONCILIATION`, `RECOVERED`, `ESCALATED`, `FAILED`).
- [2026-08-29] B2B Receivables Domain Separation: `RiskType.RECEIVABLE_OVERDUE` represents the business trigger domain, while `RootCauseEnum` determines playbook selection (`receivable_overdue`, `promise_to_pay_missed`, `chronic_non_payer`). Existing payment recovery playbook `recent_overdue: ["reminder", "payment_link"]` remains strictly untouched.
